# Requirements Document

## Introduction

This feature expands the AS Finance LMS test automation suite with three new test areas that address gaps identified in the QA coverage plan: API load/performance testing, Pact consumer-driven contract testing, and chaos/fault injection testing. These additions strengthen confidence in system behavior under stress, ensure frontend-API contract stability, and verify resilience when infrastructure components fail during critical finance operations.

## Glossary

- **Load_Test_Runner**: The k6-based load testing tool that executes HTTP requests against the API at configurable concurrency and duration levels
- **Pact_Broker**: The service that stores and verifies consumer-driven contract (Pact) files between the Frontend_Consumer and the API_Provider
- **Frontend_Consumer**: The Next.js web application that consumes the API, acting as the Pact consumer that defines expected interactions
- **API_Provider**: The NestJS backend API that serves responses, acting as the Pact provider that verifies consumer expectations
- **Chaos_Test_Harness**: The test infrastructure that simulates infrastructure failures (database outages, S3 unavailability, network errors) during finance operations
- **VU**: Virtual User — a simulated concurrent user in load testing
- **P95_Latency**: The 95th percentile response time — 95% of requests complete within this duration
- **Pact_File**: A JSON contract file generated by the consumer that describes expected request/response interactions
- **Fault_Injection**: The deliberate introduction of infrastructure failures (DB disconnect, S3 timeout, network error) into the test environment
- **Collection_Endpoint**: POST /collections — the API endpoint for posting loan payment collections
- **Disbursement_Endpoint**: POST /disbursements — the API endpoint for loan disbursement
- **Reversal_Endpoint**: POST /reversals — the API endpoint for reversing a posted collection
- **Report_Endpoint**: GET /reports/:type — the API endpoint for generating financial reports
- **Finance_Transaction**: Any atomic operation that affects money: collection, disbursement, reversal, penalty posting, or foreclosure

## Requirements

### Requirement 1: k6 Load Test Infrastructure

**User Story:** As a developer, I want a k6 load testing framework configured in the monorepo, so that I can run reproducible performance tests against the API.

#### Acceptance Criteria

1. THE Load_Test_Runner SHALL provide a k6 configuration file at `apps/api/test/load/` with configurable VU count, duration, and target base URL
2. THE Load_Test_Runner SHALL support execution via a `test:load` npm script in the API package.json
3. THE Load_Test_Runner SHALL export test results in JSON summary format including request count, error rate, P95_Latency, and throughput (requests per second)
4. THE Load_Test_Runner SHALL authenticate requests using valid JWT tokens obtained from the test seed users
5. THE Load_Test_Runner SHALL use test data factories to generate valid request payloads for each endpoint under test

### Requirement 2: Collection Posting Load Test

**User Story:** As a developer, I want to verify that the collection posting endpoint handles concurrent payment submissions without data corruption, so that field officers can safely post collections simultaneously.

#### Acceptance Criteria

1. WHEN 20 VUs submit collection requests concurrently for 60 seconds, THE Load_Test_Runner SHALL report an error rate below 5% (excluding expected 409 conflict responses)
2. WHEN 20 VUs submit collection requests concurrently for 60 seconds, THE Load_Test_Runner SHALL report P95_Latency below 2000 milliseconds for the Collection_Endpoint
3. WHEN concurrent collection requests use the same idempotency key, THE Load_Test_Runner SHALL verify that only one collection record is created per unique idempotency key
4. WHEN the load test completes, THE Load_Test_Runner SHALL verify that the sum of all successful collection allocations equals the sum of all posted payment amounts (allocation preservation invariant)

### Requirement 3: Concurrent Payment and Report Generation Load Test

**User Story:** As a developer, I want to verify that report generation remains responsive while concurrent payments are being processed, so that accountants can generate reports during peak collection hours.

#### Acceptance Criteria

1. WHEN 10 VUs post collections and 5 VUs request report generation concurrently for 60 seconds, THE Load_Test_Runner SHALL report P95_Latency below 5000 milliseconds for the Report_Endpoint
2. WHEN 10 VUs post collections and 5 VUs request report generation concurrently, THE Load_Test_Runner SHALL report zero HTTP 500 errors on the Report_Endpoint
3. WHEN the mixed-workload load test completes, THE Load_Test_Runner SHALL report overall API error rate below 5%

### Requirement 4: Disbursement and Reversal Load Test

**User Story:** As a developer, I want to verify that disbursement and reversal endpoints handle concurrent requests safely, so that managers can process approvals and corrections under load.

#### Acceptance Criteria

1. WHEN 10 VUs submit disbursement requests concurrently for 30 seconds, THE Load_Test_Runner SHALL report P95_Latency below 3000 milliseconds for the Disbursement_Endpoint
2. WHEN 5 VUs submit reversal requests concurrently for 30 seconds, THE Load_Test_Runner SHALL report P95_Latency below 3000 milliseconds for the Reversal_Endpoint
3. WHEN concurrent disbursement requests target the same loan with the same idempotency key, THE Load_Test_Runner SHALL verify that only one disbursement record is created
4. WHEN concurrent reversal requests target the same collection with the same idempotency key, THE Load_Test_Runner SHALL verify that only one reversal record is created


### Requirement 5: Pact Consumer Contract Generation

**User Story:** As a frontend developer, I want Pact consumer tests that define the expected API interactions for critical finance pages, so that API changes that break the frontend are caught before deployment.

#### Acceptance Criteria

1. THE Frontend_Consumer SHALL generate Pact_Files for the following interaction groups: authentication (login/refresh), customer CRUD, loan lifecycle (create/approve/disburse), collection posting, reversal, report generation, and loan schedule retrieval
2. WHEN a Pact consumer test runs, THE Frontend_Consumer SHALL define the expected request method, path, headers, and body for each interaction
3. WHEN a Pact consumer test runs, THE Frontend_Consumer SHALL define the expected response status code, content type, and body structure (field names and types) for each interaction
4. THE Frontend_Consumer SHALL generate Pact_Files in the `apps/web/test/pact/pacts/` directory in Pact v3 specification format
5. THE Frontend_Consumer SHALL include interactions that verify money fields are returned as integer paise (not float or string) in all finance-related responses

### Requirement 6: Pact Provider Verification

**User Story:** As a backend developer, I want the API to verify all consumer-generated Pact contracts, so that I know my API changes satisfy frontend expectations.

#### Acceptance Criteria

1. THE API_Provider SHALL verify all Pact_Files generated by the Frontend_Consumer against the running API server
2. WHEN a Pact_File contains an interaction for a protected endpoint, THE API_Provider SHALL supply valid JWT tokens for the required role during verification
3. WHEN a Pact_File contains an interaction with state requirements (e.g., "a loan exists in active status"), THE API_Provider SHALL set up the required test data via provider state handlers before verification
4. THE API_Provider SHALL execute provider verification via a `test:pact:verify` npm script in the API package.json
5. IF a provider verification fails, THEN THE API_Provider SHALL report the failing interaction name, expected response, and actual response

### Requirement 7: Pact Contract for Collection Posting Interaction

**User Story:** As a developer, I want a Pact contract that precisely defines the collection posting request/response shape, so that frontend form submissions and API responses stay in sync.

#### Acceptance Criteria

1. THE Frontend_Consumer SHALL define a Pact interaction for POST /collections that includes loanId (string), amountPaise (integer), paymentDate (string), paymentMode (string), and idempotencyKey (string) in the request body
2. THE Frontend_Consumer SHALL define the expected 201 response body containing collectionId (string), loanNumber (string), amountPaise (integer), allocations object with penaltyPaise (integer), interestPaise (integer), principalPaise (integer), and outstandingAfterPaise (integer)
3. THE Frontend_Consumer SHALL define a Pact interaction for POST /collections with missing required fields that expects a 400 response with statusCode and message fields
4. THE Frontend_Consumer SHALL define a Pact interaction for POST /collections without authentication that expects a 401 response

### Requirement 8: Pact Contract for Loan Schedule Retrieval

**User Story:** As a developer, I want a Pact contract for the loan detail and schedule endpoint, so that the loan detail page always receives the expected installment structure.

#### Acceptance Criteria

1. THE Frontend_Consumer SHALL define a Pact interaction for GET /loans/:id that expects a response containing loan_number (string), principal_paise (integer), status (string), cached_outstanding_paise (integer), and a schedules array
2. THE Frontend_Consumer SHALL define the expected schedule installment structure containing installment_number (integer), due_date (string), principal_paise (integer), interest_paise (integer), total_paise (integer), and status (string)
3. THE Frontend_Consumer SHALL define a Pact interaction for GET /loans/:id with a non-existent ID that expects a 404 response

### Requirement 9: Database Failure During Collection Posting

**User Story:** As a developer, I want to verify that a database failure mid-transaction during collection posting leaves no partial state, so that the atomic finance action invariant holds under infrastructure failure.

#### Acceptance Criteria

1. WHEN the database connection drops during a collection posting transaction (after allocation but before commit), THE Chaos_Test_Harness SHALL verify that no collection record, allocation record, journal entry, or receipt is persisted
2. WHEN the database connection drops during a collection posting transaction, THE Chaos_Test_Harness SHALL verify that the loan outstanding balance remains unchanged from its pre-transaction value
3. WHEN the database connection is restored after a mid-transaction failure, THE Chaos_Test_Harness SHALL verify that a subsequent collection posting with a new idempotency key succeeds and produces correct allocations
4. IF a database timeout occurs during collection posting, THEN THE Chaos_Test_Harness SHALL verify that the API returns an appropriate error response (500 or 503) with a correlation request ID

### Requirement 10: S3 Outage During Document Upload

**User Story:** As a developer, I want to verify that S3 storage unavailability during document upload does not corrupt customer or loan records, so that finance operations remain safe when storage fails.

#### Acceptance Criteria

1. WHEN the S3-compatible storage is unavailable during a document upload request, THE Chaos_Test_Harness SHALL verify that the API returns an error response without creating a partial document record in the database
2. WHEN the S3-compatible storage is unavailable, THE Chaos_Test_Harness SHALL verify that customer CRUD operations and loan operations continue to function without errors
3. WHEN the S3-compatible storage becomes available after an outage, THE Chaos_Test_Harness SHALL verify that document upload succeeds and the uploaded document is retrievable via signed URL

### Requirement 11: Database Failure During Reversal

**User Story:** As a developer, I want to verify that a database failure during reversal leaves the original collection intact and the ledger balanced, so that reversal atomicity is guaranteed under failure.

#### Acceptance Criteria

1. WHEN the database connection drops during a reversal transaction (after creating compensating entries but before commit), THE Chaos_Test_Harness SHALL verify that the original collection status remains "posted" (not "reversed")
2. WHEN the database connection drops during a reversal transaction, THE Chaos_Test_Harness SHALL verify that no compensating journal entries or reverse allocation records are persisted
3. WHEN the database connection drops during a reversal transaction, THE Chaos_Test_Harness SHALL verify that the ledger trial balance (total debits equals total credits) remains unchanged
4. WHEN the database connection is restored after a failed reversal, THE Chaos_Test_Harness SHALL verify that retrying the reversal with a new idempotency key succeeds and produces correct compensating entries

### Requirement 12: Network Latency and Timeout During Finance Operations

**User Story:** As a developer, I want to verify that high network latency and connection timeouts during finance operations are handled gracefully without data corruption, so that field officers in low-connectivity areas experience safe degradation.

#### Acceptance Criteria

1. WHEN database query latency is artificially increased to 5 seconds, THE Chaos_Test_Harness SHALL verify that collection posting either completes successfully or returns a timeout error without partial state
2. WHEN a database connection timeout occurs during disbursement, THE Chaos_Test_Harness SHALL verify that the loan status remains "approved" (not stuck in an intermediate state)
3. WHEN a database connection timeout occurs during penalty posting, THE Chaos_Test_Harness SHALL verify that no orphaned penalty record exists without a corresponding journal entry

### Requirement 13: SMS Provider Failure Isolation

**User Story:** As a developer, I want to verify that SMS notification provider failures do not affect finance transaction completion, so that the outbox pattern correctly isolates notification dispatch from finance operations.

#### Acceptance Criteria

1. WHEN the SMS provider is unreachable during a collection posting, THE Chaos_Test_Harness SHALL verify that the collection, allocation, journal entry, and receipt are all persisted successfully
2. WHEN the SMS provider is unreachable during a collection posting, THE Chaos_Test_Harness SHALL verify that an outbox message is enqueued for later retry
3. WHEN the SMS provider is unreachable during disbursement, THE Chaos_Test_Harness SHALL verify that the disbursement completes and the loan status transitions to "active"

### Requirement 14: Chaos Test Infrastructure and Configuration

**User Story:** As a developer, I want a reusable chaos test harness with configurable fault injection, so that I can simulate infrastructure failures in a controlled and repeatable manner.

#### Acceptance Criteria

1. THE Chaos_Test_Harness SHALL provide helper functions to simulate database connection drops, database query timeouts, S3 unavailability, and SMS provider failures
2. THE Chaos_Test_Harness SHALL restore all injected faults after each test case to prevent test pollution
3. THE Chaos_Test_Harness SHALL be executable via a `test:chaos` npm script in the API package.json using the Vitest integration test configuration (single fork, sequential execution)
4. THE Chaos_Test_Harness SHALL use the existing test factories and seed data infrastructure from `packages/testing/` and `apps/api/test/helpers/`
5. THE Chaos_Test_Harness SHALL verify database state assertions using the existing `createDbUtils` helper from `apps/api/test/helpers/db-utils.ts`
